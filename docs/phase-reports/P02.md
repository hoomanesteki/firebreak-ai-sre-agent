# Phase 02: Bundles, library, splits, leakage controls

## Summary

Phase 2 builds the thing every later number depends on: a way to record an
incident so that it can be replayed, verified, and graded, with the answer
kept somewhere the agent cannot reach.

The library of 120 scenarios is written and validated. The recorder, the
bundle format, the label store, and the leakage controls are built and
tested. What has not happened is the recording itself, which needs a machine
decision that is still open.

Most of the work here is about making mistakes loud. A bundle that changed
after recording, a reset that silently did nothing, a scenario whose label
cannot be scored, a held out family that quietly appears in training: none
of these crash, and all of them turn a published accuracy figure into
fiction.

## What was built

- **Contracts.** `lab/scenario.py` (the recipe for one incident),
  `lab/bundle.py` (the frozen result), and `firebreak_eval_labels` (the
  answer, deliberately a separate top level package).
- **Leakage controls.** `scripts/check_leakage.py` plus
  `config/leakage.yaml`, wired into `make verify`, CI, and pre-commit.
- **Recording.** `lab/recorder.py`, `lab/export.py`, `lab/bundle_writer.py`,
  and `lab/synthetic.py` for a valid but fake bundle to test against.
- **The library.** 120 specifications generated by
  `scripts/generate_scenarios.py`, plus `scenarios/LIBRARY_CARD.md`.
- **Splits.** `evals/splits.py` and the checks that keep a held out set
  held out.
- **Distribution.** `lab/package.py`, archive plus checksum, verified at
  both ends.
- **Commands.** `lab library`, `lab verify-bundles`, `lab package`,
  `lab unpack`, and ADR-0003.

## The library

120 scenarios across 10 families, from `reports/lab/library.json`:

| Split | Scenarios | Families |
|---|---|---|
| train | 44 | distractor, double-fault, error-injection, health, latency, messaging, no-fault, unreachable |
| validation | 15 | the same eight |
| test_id | 31 | the same eight |
| test_ood | 30 | contention, resource |

The resource and contention families are held out entirely. That is what
separates a system that generalises from one that memorised, and it is
checked rather than intended: `require_sound_splits` fails if a scenario
from an out of distribution family appears in train or validation, and a
test runs it against the real library.

Recording the whole library takes about 36 hours of wall clock.

The library is generated, not hand written, so it is reproducible and a
reviewer reads the rules rather than 120 files. The generator reads the flag
inventory as its only source of flag truth and validates every flag before
constructing anything, because a typo costs an hour of recording before
anyone notices.

## Leakage controls

SPEC.md Section 8.4 asks for four controls. Three are complete and one is
partial, honestly:

| Control | Status | How |
|---|---|---|
| 1. Labels importable only by eval code | Met | AST walk over the import graph, so an alias or an import nested in a function cannot hide. Plus string literals, because an import rule does not stop anyone opening the path by hand |
| 2. Change log excludes fault flag flips | Met | `sanitise_changes` removes the whole record, at any nesting depth, in keys as well as values, case insensitive. The writer calls it; the leakage checker re-checks every recorded bundle |
| 3. Bundle backend reads only manifest entries | Met | `BundleReader.path_for` refuses an unlisted name and refuses a name resolving outside the bundle |
| Extra: bundle names reveal nothing | Met | Bundles are stored under an opaque id; a rule rejects any directory that is not one |
| 4. Canary scan over captured prompts | Partial | Every label carries a random canary and `find_canaries` works. There are no prompts to scan until the agent exists in Phase 6, where this is wired into the eval runner |

Scenario specifications are treated as ground truth alongside labels. The
spec only names `labels/`, but a specification contains `target_service` and
`fault_class`, which is the same answer in a different file.

## Defects found

1. **The no fault family tested nothing.** The specifications said a demand
   spike, but `fault.kind` was `none`, so the recorder would have flipped
   nothing: the scenario would have run at ordinary load, nothing would have
   alerted, and the family whose entire purpose is an alert with no service
   at fault would have measured nothing. This came from an instruction of
   mine to name the flood flag in notes only, to keep it from being scored
   as a fault. The flood is now applied as a `harmless_flag` distractor,
   which is the honest description of it: a flag change that is not the
   fault.
2. **The leakage checker double reported.** `from firebreak.lab.scenario
   import load_spec` produced two violations for one import, because both
   the module and the imported name match. Deduplicated by matched prefix.
3. **A service mapping was wrong.** `failedReadinessProbe` was mapped to
   frontend from a table. The flag's own description in the pinned demo says
   "readiness probe failure for cart service". Reading the source beat
   trusting the table.
4. **Bundles were stored under a name that gave away the answer.** This is
   the most serious one, and it was found by a test that a rate limited
   agent left behind half written. A bundle sat at
   `bundles/payment-failure-50pct-20u/<run>/`, and its manifest carried
   that same `scenario_id`, so a directory listing named the culprit, the
   fault class and the severity. No forbidden field appeared anywhere, so
   the leakage checker saw nothing: it looked for field names, and this
   was a path.

   It matters more than it first looks. SPEC.md Section 6.3 builds every
   evidence id from a hash of the query, the time range and a backend
   fingerprint, and the natural fingerprint for a replay backend is the
   bundle path. Phase 3 would have carried the answer into records the
   agent handles directly.

   Bundles are now stored under an opaque `inc_<12 hex>` derived from the
   scenario and run, the manifest carries that instead of a scenario name,
   and the mapping back lives in `labels/` with the rest of the answer.
   Real incidents are identified by a ticket number rather than by their
   cause, so this is also the more faithful design. The leakage checker
   gained a rule requiring every bundle directory to match that pattern,
   and that rule is tested against the exact directory name that started
   this. Bundle format version moved to 2.
5. **Three parallel agents raced on the filesystem** and produced 37 byte
   identical duplicate files. Each was compared against its canonical twin
   before deletion. Worth recording because it will happen again.

## Known issues

**The library has not been recorded.** This is the phase's main outstanding
item and it is blocked on a decision, not on code. 120 scenarios at about 18
minutes each is 36 hours of wall clock on a machine that can hold the stack.
The Phase 1 report measured this one as having no headroom: 7.9 GB of
declared limits against 7.8 GB allocated to Docker, with Prometheus
ingestion stalling under load.

**Two of the three exporters are not written.** `export.py` implements
Prometheus. The Jaeger and OpenSearch query APIs have not been confirmed
against the pinned release, and SPEC.md rule 3 says APIs are confirmed
rather than assumed. They are the first task of Phase 3, which is where the
spec puts backends anyway, and no real recording can happen before then.

**The OpenSearch logs exporter in the collector is still failing**, carried
over from Phase 1. Logs are a Phase 3 signal.

**Synthetic bundles are not real data.** `lab/synthetic.py` says so in its
first line. It exists so the tool layer can be built and tested before the
library is recorded. No number that reaches a report may come from it, and
the honest way to keep that true is to record the library before Phase 5
produces any measurement.

## Open questions for the owner

1. **Where does the library get recorded?** Unchanged from Phase 1 and now
   blocking. A machine with 16 GB for Docker would remove the ingestion
   stalls and let 36 hours of recording run unattended. Options: a cloud VM,
   this machine overnight in batches, or a smaller first pass of about 30
   scenarios to unblock Phases 3 to 5 and record the rest later.
2. **Is 36 hours acceptable, or should the timings shrink?** The default is
   300 seconds of warmup, 600 of fault, 180 of cooldown. Halving the fault
   window would roughly halve the total, at the cost of fewer samples per
   incident.
3. `gh auth login`, still outstanding, still one command.
