# Phase 9: Remediation, approval, recovery, security

## Summary

This is the first phase where Firebreak can change the system it investigates, so
the work is mostly about making sure it cannot do so by itself. It cannot: the
agent's import graph reaches nothing that writes, the action space is a three-entry
allowlist, and a separate process makes every change after a person decides with a
required reason.

The two acceptance criteria that name a test both hold. Agent processes reach no
writer at any import depth. Double approval executes once, and still does after a
restart, because the state that prevents it is the audit chain rather than anything
in memory.

The interrupt that ADR-0008 deferred from Phase 6 is built, and it is the only
`StateGraph` in Firebreak. That ADR argued the investigation loop did not need the
abstraction and named the approval wait as where that changes; this phase keeps the
argument rather than quietly extending the deferral.

What is not done is the live half. Remediation execution against the running demo,
and the recorded live recovery demo, need the stack and AC power. The executors are
injected and tested with stand-ins, which leaves the demo execution path the largest
untested surface in the phase, and the report says so rather than implying otherwise.

## What was built

**Proposals** (`remediation/proposal.py`). A frozen object with no client, no
credential, and two methods, both read-only. Its id is a hash of the action and its
target, excluding the rationale and the timestamp, which is what makes double
approval safe.

**The audit chain** (`remediation/audit.py`). JSON Lines, append-only, each record
carrying the hash of the one before. `verify_chain` returns the first broken link
rather than a boolean. Executed is recorded separately from approved, and a failed
execution is recorded before the failure is returned.

**The approval service** (`remediation/approval.py`). Requires a reason, re-checks
the allowlist, executes at most once per proposal, and shows a reviewer the re-read
evidence as a separate field from the agent's rationale. With no executor it records
the decision and changes nothing, which is how bundle mode grades proposals without
performing them.

**The durable workflow** (`remediation/workflow.py`). A `StateGraph` with a
checkpointer: record, wait for a person, carry out, check recovery. The thread id is
the proposal id.

**Recovery verification** (`remediation/recovery.py`). Three outcomes, compared
against the incident's own baseline, requiring three consecutive samples inside
tolerance.

**`propose_remediation`** (`tools/remediation.py`). The commander's tool only.
Refuses an evidence id the investigation never gathered.

**Untrusted-input controls** (`security/injection.py`). Wrapping, classifying and
withholding, in that order of reliability. Wired into both log tools so the agent
reads redacted text while the evidence record keeps the raw line.

**The injected-log suite** (`scenarios/injectors/payloads.yaml`,
`tests/security/test_injection_suite.py`). Eight crafted payloads and ten normal
lines chosen to overlap the patterns.

**The threat model** (`docs/threat-model.md`) and **ADR-0011**.

## Evidence

Commands and results:

- `make verify`: green.
- `uv run pytest tests/security -q`: 31 tests. 13 on the privilege boundary, 18 on
  injection.
- `uv run pytest tests/integration/test_approval_workflow.py -q`: 20 tests covering
  interrupt, resume, rejection, restart, and bundle mode.

One end-to-end run of the durable workflow, with a stand-in executor:

```
1. waiting: True | shown: set flag paymentFailure to off | reversible: True
   executed while waiting: []
2. outcome: executed | executed: ['rem_1c1a6a0096c6']
   recovery: recovered
3. chain verifies: True
   decisions: ['proposed', 'approved', 'executed']
```

The second line is the one that matters: nothing had been executed while the
workflow was waiting for a person.

Injected-log suite, the four numbers SPEC.md Section 11 asks for:

| metric | value |
|---|---|
| payloads detected | 8 of 8 |
| false positives on normal logs | 0 of 10 |
| unauthorised proposals | 0 |
| reports repeating an injected claim | not measured, needs a model |

**Both rates are properties of this suite, not of the space of attacks.** The suite
was written by the same person who wrote the classifier, which is the weakest thing
about those two numbers, and `docs/threat-model.md` says so in its own words. The
unauthorised-proposal count is the number that does not depend on the classifier:
the allowlist has three entries, so an instruction to do anything else cannot become
a proposal however it is phrased, and the test asserting that would hold if the
classifier were deleted.

Privilege separation, what the import walk actually checks:

| check | result |
|---|---|
| agent modules importing a writer directly | none |
| writers reachable from the agent at any depth | none |
| agent modules importing `subprocess` or `docker` | none |
| agent can reach `remediation.proposal` | yes, so the test is not vacuous |
| every module named in `WRITERS` exists | yes, so a rename cannot hollow it out |

## Deviations from the spec (with ADR links)

**Only the approval workflow is a `StateGraph`** (ADR-0011, ADR-0008). A checkpointer
earns its cost when execution stops and resumes in another process. The
investigation loop runs to completion in one, so wiring it into a graph would be the
abstraction's cost with none of its benefit.

**The audit chain is tamper evident rather than tamper proof** (ADR-0011). Signing
needs a key this project does not have, and claiming tamper proofing without one
would be worse than claiming the weaker property accurately.

**Log redaction applies to what the agent reads, not to the evidence record.** The
approval service shows a human raw evidence, and exit gate check 2 re-runs a record
and compares hashes. Redacting the record would hide what a service actually logged
and would make every re-execution check depend on the classifier's current patterns.

## Known issues

**The demo execution path is untested.** Executors are injected and every test uses
a stand-in. Turning a real flag off through flagd and restarting a real container
have never been exercised, which is the largest untested surface in this phase.

**The classifier's rates are self-measured.** Eight of eight and zero of ten are real
measurements against a suite whose author also wrote the detector. A payload written
after reading `security/injection.py` would very likely get through. The reason that
is tolerable is that getting through means being shown to a model that cannot act.

**Nothing measures whether a model repeats an injected claim.** That is one of the
four metrics SPEC.md Section 11 asks for, and it needs a model.

**ASI06 memory poisoning has no control yet.** Incident memory arrives in Phase 10,
and the threat model records the row as not built rather than omitting it.

## Open questions for the owner

1. **Model credentials.** Still the gate on the fourth injection metric, on the cost
   table, on the judge's calibration, and on every comparison between configurations.
2. **AC power and the live stack.** Needed for the live recovery demo, for the
   injected-log sidecar against a real recording, and for the remaining 30 hours of
   library recording. The library is eight bundles.
3. **Who operates the approval service**, and under what authentication. The audit
   record's `actor` is free text on purpose: inventing an identity model here would
   be a fiction the audit log then records as fact.
4. **An independent red team pass.** The most useful thing anybody could do to the
   numbers in this phase is try to beat the classifier without having read it.
