# Phase 8: Cascade, fallback, ablations, CI gate

## Summary

The cascade, the fallback policy and the deterministic floor are built, along with
ablations A2, A3 and A4, the judge with its rubric and blind calibration, and the
two-part eval gate workflow. Everything that needed a model to measure is
measurable and unmeasured, and this report says which is which rather than
reporting stub numbers as results.

Three things this phase found are worth reading before the acceptance table.

**CI failed on a commit whose tests passed locally, and the reason generalises.**
mypy narrows `sys.platform` to the platform it is checking for, so code behind a
platform guard is only half checked by one run: on macOS the guard's else branch is
unreachable, on Linux the body is, and `warn_unreachable` turns whichever half is
dead into an error. `make verify` and CI now both check darwin, linux and win32.

**The eval gate workflow could not have used its own credentials.**
`firebreak.agent.llm` tells a user to set `LLM_BASE_URL` and `LLM_API_KEY`, and
`Settings` read only the `FIREBREAK_` prefixed forms. Following the instruction did
nothing and the process stayed in stub mode, which reports nothing because stub is a
valid mode. This is the seventh time in this project that two places agreed on a
concept and disagreed on its name.

**The spec conformance checker found work a completed phase had left out.** It
reads SPEC.md Sections 9.5, 14 and 17 and checks the repository against them. On
the day it was written it found `make eval`, which CLAUDE.md promises and nobody had
added since Phase 5.

## What was built

**Model tiers** (`config/models.yaml`, `agent/models.py`). Three tiers, each an
ordered list. No models are listed: SPEC.md's own table says "owner chooses; verify
names", and an invented id fails at the first call while an invented price silently
multiplies every cost figure in every report. A price is rejected without a source
and a date it was checked, which is Phase 8's reviewer focus turned into a rule.

**The cascade** (`agent/cascade.py`). Escalation on two schema failures, low
reported confidence, or a contradiction between specialists. Fallback on timeouts,
429s and 5xx, with exponential backoff and full jitter per [R27]. A schema error is
never retried and a transport error never escalates, enforced both in the
configuration model and at the point of use.

**The deterministic floor** (`agent/floor.py`). B0's findings published with
"Automated triage only, no AI analysis" and a sentence saying whether the models
were unreachable, the budget ran out, or the investigation failed, because those
need different responses from an operator.

**Ablations A2, A3, A4** (`AgentOptions`). Switches on the one graph. A2 removes the
dependency tools as well as the ranking, since Section 9.5 gives A2 "no ranking, no
dependency tools" and leaving the tools in would make it a weaker version of
baseline B1.

**The judge** (`evals/judge.py`). A rubric as data rather than prose in a prompt,
three verdicts rather than a score, Cohen's kappa rather than raw agreement, and a
blind sheet carrying no verdicts and no scenario names.

**The eval gate** (`.github/workflows/eval-gate.yml`, `firebreak eval gate`,
`scripts/eval_regression.py`). A deterministic half on every relevant pull request
and a model half behind the `run-evals` label and credentials, which writes a
SKIPPED comment saying why when there are none.

**CI and repository tooling** (`scripts/ci_status.py`,
`scripts/check_spec_conformance.py`, `make ci-status`, `make spec-check`). Described
in the Summary.

### Transcript review, fifteen runs

SPEC.md Section 17 Phase 8 asks for this. Eight recorded bundles and seven fixture
runs chosen to exercise paths the recordings do not reach. Stub mode throughout, so
what follows is about the harness, the ranking and the gates.

Recorded, eight runs:

| bundle | truth | fault class | named | top 3 | rounds |
|---|---|---|---|---|---|
| inc_b05f790aa07a | shipping | latency | **shipping** | shipping, quote, astronomy-db | 1 |
| inc_db1f0b59802b | checkout | queue_lag | fraud-detection | fraud-detection, accounting, product-catalog | 1 |
| inc_097616f9db82 | payment | error_injection | abstained | frontend, payment, checkout | 0 |
| inc_bf438da8ac5a | payment | error_injection | abstained | frontend, payment, checkout | 0 |
| inc_d7d3dd51e373 | payment | error_injection | abstained | frontend, payment, checkout | 0 |
| inc_e68fef497434 | cart | health_check_failure | abstained | product-catalog, payment, frontend | 0 |
| inc_fc248619f412 | shipping | latency | abstained | product-catalog, astronomy-db, frontend | 0 |
| inc_116d45ef18fd | none | none | abstained | payment, frontend, product-catalog | 0 |

What the wins showed: one clean win, `inc_b05f790aa07a`, a latency fault on
shipping named correctly with shipping ranked first. It is also the one recorded
bundle whose anomaly score was large enough to get past triage and still point at
the culprit.

What the failures showed, and this is the substantive finding of the review:

- **Six of eight runs ended with zero rounds.** Triage abstained and the agent never
  executed. That is why every configuration scores identically in the eval: on six
  of eight bundles they are all B0. The abstention threshold is the bottleneck for
  the entire system, not just for the no-fault family.
- **All three payment-failure recordings rank `frontend` first with `payment`
  second.** The same order three times is not noise. The graph walk exists to
  prevent exactly this symptom-over-cause ranking, and on real telemetry it is not
  preventing it.
- **`inc_db1f0b59802b` is the dangerous case.** It did not abstain, and it named
  fraud-detection when the truth was checkout. A confident wrong answer is what
  SPEC.md Section 1 calls worse than no agent, and this is the only recorded run
  that produced one.
- **Two culprits were not in the top three at all**: cart on a health check failure,
  and shipping on the distractor latency scenario. Both are cases where the loudest
  service is not the broken one.

What the abstentions showed: the one no-fault recording abstained correctly, and so
did five faulted recordings that should not have. The abstention rule is not
discriminating between healthy and broken; it is discriminating between loud and
quiet, and on this library that is a different question.

Fixtures, seven runs, each exercising one path:

| variant | named | outcome |
|---|---|---|
| normal, error injection | payment | correct, gate passed, 5 claims |
| normal, no fault | abstained | correct |
| double fault | payment | named the primary fault |
| tight budget (1 round) | payment | stopped on `budget_steps`, still reported |
| no models | payment | floor engaged, labelled, 4 claims citing B0 evidence |
| no graph (A2) | payment | still correct on fixtures |
| fabricating reporter | payment | **gate removed exactly the 1 invented claim, kept 5** |

The last row is the exit gate catching a fabrication end to end in a real run
rather than in a unit test: a reporter that added a claim citing
`ev_metric_deadbeefdead` lost that claim and nothing else. The no-models row is the
floor's acceptance criterion demonstrated the same way.

The no-graph row is worth one caution. A2 stays correct on fixtures and abstains on
the recorded bundle it was tried against, which is consistent with the recurring
finding that fixtures are a different scale from reality rather than merely easier.

## Deviations from the spec (with ADR links)

**No learned router**, despite [R11] and [R12] (ADR-0009). Both results are about
learned routers, and eight recorded incidents is not a training set. The rule-based
cascade is what a learned router would have to beat, and the cost table is what
would justify building one.

**A2 removes the dependency tools, not only the ranking.** Section 9.5's wording
gives A2 both. Leaving the tools in would have made A2 a weaker baseline B1.

**The gate returns INCONCLUSIVE on validation** and exits non-zero (ADR-0012). Eight
recorded bundles against a minimum of ten. This is the designed answer, not a
failure to run.

## Known issues

**The abstention threshold is the system's bottleneck.** Six of eight recorded runs
never reached the agent. Phase 7 recorded the measurement and the reason it cannot
be retuned yet; this phase's transcript review shows the consequence, which is that
no comparison between configurations can distinguish them on those six bundles.

**The ranking blames the entry point.** Three recordings, same wrong first place.
Worth a measurement pass of its own, and it needs more recordings.

**A confident wrong answer exists in the library.** One recorded run named the wrong
service without abstaining. That is the failure mode this project is built to avoid,
and it is now a known, reproducible case rather than a worry.

**Two Phase 8 commits landed on the Phase 7 branch** before the branch split, the CI
tooling and the model cascade. Both are green and coherent, so they were merged
rather than surgically moved.
