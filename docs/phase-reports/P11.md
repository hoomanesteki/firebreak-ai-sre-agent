# Phase 11: Agent observability and Console

## Summary

The first phase whose output is meant to be looked at rather than measured, and the first
where the honest answer to "does this work" is yes rather than "the mechanism exists and
cannot be measured".

One investigation now produces one trace with node, tool and model child spans, carrying no
prompt content. Six Console pages render with data and without, and every claim on the
Report page links to the query, window and rows behind it. `make demo-offline` replays ten
showcase incidents from recorded model answers with no model and no network, and fails if
any of them stops reproducing.

**The most useful thing built here is that the demo works on a fresh clone.** The recorded
library is git-ignored and averages 7.6 MB per bundle, 61 MB for the eight recorded so far and
roughly 870 MB for all one hundred and fourteen, so a demo keyed to it would run on one
machine.
The showcase is ten scenario specs rebuilt deterministically instead, which is what lets CI
check it rather than skip it. Every unmeasurable result in the last four phase reports traces
back to having no model; this does not fix that, and it does mean the whole path is
demonstrable and reproducible by anyone who clones the repository.

**Two things are deliberately not built and the pages say so.** Live streaming, because
against a frozen bundle an investigation finishes in under a second and a progress bar would
be theatre. And the vendored chart libraries, because there is no calibration curve with
enough data to plot.

## What was built

**Agent spans** (`telemetry/spans.py`). `gen_ai.*` attribute names imported from the
installed semantic conventions package rather than typed as literals. One investigation, one
trace, enforced by a context manager so children are children by construction.

**The no-content rule.** Spans carry shapes: which node, which tool, which tier, tokens,
rows. A prompt becomes a twelve character hash plus its version stamp. An error records the
exception type and not its message, because a tool's message can quote the data that caused
it. `include_content` exists for local debugging, is off, and writes its own value onto every
root span so a trace says whether it is carrying content.

**Replay cassettes** (`scripts/record_cassettes.py`). 56 cassettes across the ten showcase
incidents, keyed by a hash of purpose and payload so they survive the loop asking its
questions in a different order.

**The showcase** (`demo/showcase.py`). Ten scenario specs with a stated reason each, rebuilt
deterministically with a fixed run id and seed. Two are no-fault incidents where abstaining
is correct, one is a distractor, one is a double fault.

**The offline demo** (`scripts/demo_offline.py`, `make demo-offline`). Replays each showcase
incident and compares the result with what was recorded. A mismatch fails rather than warns.
Wired into `make verify` and into CI.

**The Console** (`web/app.py`, six templates, `web/store.py`, `make console`). Incidents,
Investigation, Report, Approvals, Evaluation, Feedback. Reads files and computes nothing.

**ADR-0014**, on why the two telemetry pipelines are separated in both directions and why the
Console computes nothing.

### Transcripts reviewed

The template asks what wins, failures and abstentions showed. Reading them is how the worst
finding in this phase surfaced.

**The abstentions are the best writing the system produces.** From
`inc_92856323819d`, whole and unedited:

> No service was unusual enough to investigate. The largest anomaly anywhere was 1.0 robust
> deviations, below the 22.7 threshold.

Zero rounds, zero tool calls, a stated measurement, a stated threshold, and no hedging. A
reader can disagree with the threshold, which is the property that makes it useful.

**The wins say nothing.** All five claims from `inc_9bd8b1af412c`, the clearest fault in the
set, whole:

> payment is the most likely root cause, with 5 piece(s) of supporting evidence.
> metrics_analyst found signal for payment in 1 evidence record(s).
> logs_analyst found signal for payment in 1 evidence record(s).
> traces_analyst found signal for payment in 1 evidence record(s).
> change_analyst found signal for payment in 2 evidence record(s).

Every one is true, every one cites evidence that re-runs identically, and not one says what
broke. Four of the five describe the investigation rather than the incident. This is a
minute of an internal meeting, not an explanation, and a reader learns nothing from it that
the service name did not already carry.

**Four of the six gate checks are vacuous on this data, and the gate still reports a pass.**
Across all ten reports: 40 claims, every one typed `mechanism`, and **zero carrying a
number.** No `measurement`, `timeline` or `blast_radius` claim exists anywhere in the set. So
the numbers check verifies nothing, the blast-radius provenance check has nothing whose
provenance to check, and the gate's own detail line says so plainly:

> numbers: all 0 cited number(s) match

That detail string is good design, since a vacuous pass that announces itself is recoverable.
The demo's `gate=pass` column is not: it reads as six checks passing when two verified
something and four had nothing to look at.

**The cause is the stub, and that does not make it harmless.** The deterministic stub emits
templated mechanism claims, so this is what a replay of stub answers looks like rather than
what the system does with a model. It does mean the only end-to-end exercise of the exit gate
that CI runs is one where two thirds of it is inert, and that the gate has no check for
whether a claim asserts anything at all. Six checks cover whether a claim is *supported*.
None covers whether it is *informative*, and a report of five supported tautologies passes
cleanly.

Whether to add a seventh check is for the owner and is recorded in the open questions.

**The Approvals page has no seeded case, and the row above should not be read as one.**
The audit chain holds zero records, because remediation runs in live mode only and there is
no live mode without credentials. Both columns render the same page, and the only reason it
counts as tested is that the paragraph saying Firebreak cannot execute from this page renders
either way. Whether it renders a queue correctly is untested against real records, and the
integration tests seed their own.

Evidence links, which is the third acceptance criterion, measured across all ten stored
reports: **40 claims, 80 citations, 80 links rendered and 80 returning 200.** Each record
carries `query`, `window`, `fingerprint`, `result_sha256`, `tool` and `arguments`, so a reader
can re-run it rather than read a rendering of it. An invented evidence id returns 404 rather
than an empty panel.

## Deviations from the spec (with ADR links)

**No metrics, no collector config, no Grafana dashboards** (ADR-0014). These three form one
gap rather than three: a dashboard needs a pipeline, a pipeline needs a collector, and a
collector needs something to receive. Nothing runs one here. Shipping a collector config and
dashboard JSON that nobody has ever pointed at a running backend would be three untested
files that look like a working observability stack, which is worse than a recorded gap.

**No live streaming** (ADR-0014). Against a frozen bundle an investigation finishes in under
a second.

**Chart.js and Cytoscape.js not vendored** (ADR-0014). One graph worth drawing and no
calibration curve with enough data to plot.

**Fonts not self-hosted.** SPEC.md Section 6.13 names Sora and JetBrains Mono. The stack
falls back to system faces rather than fetching from a CDN, because a web request would break
the offline demo, which is the one thing this Console has to work for. Vendoring them is a
licence check and two files.

**The showcase is fixtures, not recordings.** ADR-0014. The alternative was a demo that runs
on one machine.

## Known issues

**The demo's numbers are fixture numbers and look far better than the real ones.** Eight of
eight against one of seven. A reader who takes the demo for a benchmark takes away a figure
roughly six times better than the measured one. The demo says it is replaying stub answers, and the fixture
caveat is in this report and in `demo/showcase.py`, and it is still the most likely thing for
a reader to take the wrong way.

**The gate's own end-to-end exercise in CI is two thirds inert.** Recorded in full under
Transcripts reviewed: 40 claims across ten reports, all typed `mechanism`, none carrying a
number, so the numbers and blast-radius checks verify nothing on the only data CI runs the
gate against.

**`firebreak.node` held two vocabularies until this phase closed.** Found by counting spans
to check this report's own numbers rather than by a test: the four analyst nodes all send
the `specialist` prompt, and the model span recorded that prompt name under the node
attribute, so grouping by node produced a phantom `specialist` row beside the four real
ones. The prompt name moved to `firebreak.model.purpose` and two tests now hold the
vocabularies apart. This is the ninth instance in this project of two components agreeing
on a type and disagreeing on a vocabulary, and the first one caught by writing down a
number rather than by a test.

**The observability half of this phase is a third built.** Spans work and are tested.
Nothing has ever been exported. The first time an OTLP endpoint exists, the exporter path is
untested code.

**The Console has no write path at all.** No approve button by design, and also no feedback
form, which is a gap rather than a decision: the store and its rules exist and a form over
them has not been built.

## Open questions for the owner

1. **Model credentials.** Now blocking: the cost table, the cascade comparison, the judge's
   calibration, the model half of the CI gate, GEPA, A6, and cassettes that replay a real
   investigation rather than a stub's imitation of one.
2. **AC power and the live stack.** The library is eight of one hundred and fourteen bundles.
3. **Whether an OTLP endpoint exists to point at.** A collector config and a dashboard are
   an afternoon each once there is somewhere to send spans, and untested files until then.
4. **Whether the exit gate should get a seventh check, for whether a claim says anything.**
   The transcript review above found forty supported tautologies passing cleanly. Six checks
   ask whether a claim is supported and none asks whether it is informative. A check is
   possible, requiring at least one `measurement` claim carrying a number, and it would fail
   every showcase report today, which is either the right answer or a reason not to add it
   until a model is producing the claims.
5. **`PYSEC-2026-2447`**, carried from Phase 10.
