# Phase 03: Tool layer

## Summary

The read only tool layer is built: eleven typed tools over a replay backend,
each producing evidence a verifier can re-run. The evidence mechanism that
the exit gate will depend on works, and the specialist tool boundaries are
structural rather than advisory.

Two things are not done, both blocked rather than deferred. The live Jaeger
and OpenSearch backends need their query APIs confirmed against a running
demo, and the backend parity contract tests need two backends to compare.
Both wait on a recorded library, which waits on a machine decision.

The interesting output of this phase is not the code. It is a measurement:
ranking services by metric anomaly alone finds the culprit first 60 percent
of the time and within the top three every time. That is the case for the
knowledge graph in Phase 4, and it says what the graph has to do.

## What was built

- **`tools/evidence.py`**: deterministic evidence ids, extracted facts with
  units, and records that validate their own id against their content.
- **`backends/base.py`**: the backend protocol and the caps every tool
  inherits rather than restates.
- **`backends/bundle_duckdb.py`**: the replay backend, reading Parquet
  through the manifest with bound parameters and no caller supplied SQL.
- **`tools/base.py`**: the registry, the per tool call caps, bounded results.
- **`signals.py`**: the telemetry vocabulary, declared once.
- **`triage/anomaly.py`**: median and MAD anomaly scoring.
- **`triage/log_templates.py`**: a deterministic log masker.
- **`tools/{metrics,logs,traces,topology,changes,registry}.py`**: eleven
  tools plus the specialist allowlists.
- ADR-0004 on typed tools rather than a query language.

## The tools

Eleven of the fourteen in SPEC.md Section 6.3:

| Tool | Signal |
|---|---|
| `list_anomalies` | Ranks every service against a baseline |
| `query_metric` | Samples of one named metric |
| `compare_windows` | One service, before and during, with an effect size |
| `search_logs` | Log records, literal substring matching only |
| `top_error_signatures` | Error templates with first seen times |
| `find_traces` | Representative failing or slow traces |
| `trace_breakdown` | Critical path and per span self time |
| `service_dependencies` | Upstream or downstream, bounded depth |
| `blast_radius` | Everything that transitively depends on a service |
| `recent_changes` | Deploys and config events in a window |
| `get_evidence` | Expands a stored record by id |

Three are blocked on later phases: `runbook_search` needs the knowledge
files Phase 4 writes, `similar_incidents` needs the incident memory from
Phase 10, and `propose_remediation` needs the approval service from Phase 9.

**Descriptions reviewed against SPEC.md Section 6.3.** Every description
says what the tool is for, when to reach for it, and when not to. Lengths
run from 470 to 718 characters. A test asserts each one contains a steering
away clause, and states in its own comment that it is a smell check rather
than a proof, because the real review is reading them. Two examples of the
kind of guidance that matters:

- `recent_changes`: "A change near an incident is a coincidence until the
  same service also shows an anomaly. Chasing the most recent change is the
  single most common way a human or an agent gets root cause analysis wrong,
  and this tool cannot and does not tell you that a change it returns caused
  anything."
- `get_evidence`: "Ask for the smallest number of rows that answers the
  question: pulling fifty rows into context to check one number spends the
  budget that later steps of the investigation need."

## What ranking alone can do

From `reports/triage/anomaly_only_ranking.json`, 100 trials over synthetic
fixtures, with no dependency graph:

| Family | Culprit ranked first | Within top three |
|---|---|---|
| memory leak | 20 of 20 | 20 of 20 |
| cpu saturation | 20 of 20 | 20 of 20 |
| latency | 12 of 20 | 20 of 20 |
| error injection | 4 of 20 | 20 of 20 |
| unreachable dependency | 4 of 20 | 20 of 20 |
| **overall** | **60 of 100** | **100 of 100** |

The split is the useful part. Resource faults are found first every time,
because a container metric moves on the culprit and nowhere else. Error
injection and unreachable dependency are found first in one case in five,
because the fault propagates and the caller shows the larger swing.

That is the argument for the topology ranking in SPEC.md Section 6.4, made
with numbers rather than assertion, and it tells Phase 4 what the job is:
the culprit is already a candidate every single time, so the graph has to
reorder within the top three, not find something the metrics missed.

**These figures are from synthetic fixtures.** The report file says so in its
own fields. They are a design signal and must never appear as a result.

## Defects found

Every defect in this phase was a seam defect. None broke a unit test. All
would have broken an investigation.

1. **Timestamps were rendered in the machine's local timezone.** A bundle
   anchored at 2025-01-01 UTC came back as 2024-12-31 17:13-07. Every
   evidence id is a hash over those strings, so the same bundle produced
   different ids on different machines and a verifier re-running a citation
   recorded elsewhere could never match it. My defect, introduced with the
   cast that avoided a pytz dependency.
2. **The metric vocabulary had drifted.** The exporter wrote
   `span_calls_total`, the synthetic builder wrote
   `traces_span_metrics_calls_total`. Every metric tool would have returned
   no data for half the bundles, silently.
3. **The topology edge shape had drifted.** `call_count` against
   `requests_per_second`. Every edge read as carrying no traffic. A defensive
   reader that accepted both shapes was written and then removed: tolerating
   drift is what let the first two instances go unnoticed.
4. **A no fault bundle's change log named the flood flag.** The recorder
   cleaned the log against the primary fault plus distractor flags; the
   synthetic builder computed the same set separately and forgot the
   distractors. The worst possible place to leak, since the correct answer
   for that family is that no service is at fault.
5. **Synthetic bundles carried three of seven declared metrics.** The service
   graph edges the dependency ranking needs and the container metrics the
   resource families depend on were absent, so 30 held out scenarios had no
   symptom to find.
6. **The resource families were given an error rate**, which would have made
   the hardest family the easiest. A leaking process serves correct responses
   until it dies.
7. **Latency had no jitter**, so every degraded service scored identically
   and a ranking was a set of ties.
8. **A stale metric name sat in the recorder's own test double**, unnoticed
   because the vocabulary contract only checked synthetic bundles.
9. **Four mutation gaps**: a cap asserted against the wrong error, an edge
   schema with no strictness test, and the timezone fix with no regression
   test.

The pattern is worth naming, because it will recur: the recurring failure
mode in this codebase is **two components agreeing on a type and disagreeing
on a vocabulary**. Pydantic catches the first and says nothing about the
second. The answer has been to declare each vocabulary once, in one module,
and assert in a contract test that every producer speaks it.

## Known issues

**Only one backend exists, so parity is unproven.** The protocol is written
so the second can be dropped in, and the contract tests are specified, but a
parity claim with one backend would be a claim about nothing.

**Jaeger and OpenSearch query APIs are unconfirmed.** SPEC.md rule 3 says
APIs are confirmed rather than assumed, and the demo's Jaeger is version
2.19.0, which changed its query surface from 1.x. Confirming them takes a
running stack and an hour.

**Everything measured so far is from synthetic fixtures.** That is
appropriate for building and testing tools, and it stops being appropriate
the moment Phase 5 produces a number. The library should be recorded before
the eval harness reports anything.

**The OpenSearch logs exporter in the collector still fails**, carried from
Phase 1. It is the same task as writing the OpenSearch backend.
