# Phase 01: Target system and scenario lab

## Summary

The OpenTelemetry Demo is pinned at tag 3.1.0 as a submodule, extended only
through the seams it documents, and Firebreak can now drive it: set any
feature flag and wait until flagd actually serves it, set an exact load
level and wait until the generator reaches it, and receive the resulting
Alertmanager deliveries.

The stack was started and exercised rather than only configured. That found
seven defects static review would not have: three in the composition, two in
the lab's own timing assumptions, one in CI, and one in how evidence was
stored. All seven are fixed, and the fixes that concern the running system
are verified against it.

## What was built

- `vendor/otel-demo` pinned at 3.1.0, commit `dedc0178`. Never edited.
- `docs/target-system.md`: every service, port, route, flag, and collector
  pipeline read from the pinned files, with the facts that would corrupt a
  recording called out.
- `ops/compose.live.yml`: publishes Jaeger, OpenSearch, and the flagd OFREP
  port to loopback, adds Alertmanager, relocates the flag store, turns off
  browser load users, and sets a 15 second metric export interval.
- `ops/otelcol-config-extras.yml`: the `service_graph` connector, with the
  upstream pipeline entries repeated so nothing is dropped.
- `ops/alert_rules.yml`: four rules over span metrics and dependency edges.
  `ops/alertmanager.yml`: routes everything to Firebreak's webhook.
- `src/firebreak/lab/`: `flags.py`, `load.py`, `stack.py`, `smoke.py`,
  `webhook.py`, `verify.py`, `endpoints.py`.
- `firebreak lab` commands: `flags list|get|set|reset|inventory`,
  `load set|stop|status`, `render-config`, `verify`, `webhook`, `smoke`.
- ADR-0002 (target system and pin) and ADR-0005 (service graph connector).

Reports are written per run under `reports/lab/live_verification/`, named for
the moment they ran, because a later failing run must not overwrite the
record of a passing one. Three runs across one restart are committed, and
they show the warmup rather than only the end state:

| Run | Passed | Failing checks |
|---|---|---|
| `20260919T231117Z` | 4 of 7 | service graph, span metrics, sample density |
| `20260919T231151Z` | 6 of 7 | sample density |
| `20260919T231258Z` | 7 of 7 | none, ready to record |

A stack that has just started has no telemetry yet, so the checks fail until
it does. That is the check working. It also means a recorder must call
`lab verify` and wait for a pass before it starts a scenario, rather than
assuming a started stack is a usable one.

**The alert path works end to end.** With `paymentFailure` at 100 percent,
Prometheus fired `dependency_edge_failing`, Alertmanager held three alerts,
and the webhook receiver recorded the deliveries in Alertmanager's standard
payload shape, with `status`, `alerts[]`, `labels`, `annotations`,
`startsAt`, and `groupKey`. That is the whole path Phase 6's entry gate
consumes, apart from the agent itself.

**The premise of the project is visible in the data.** The fault was
injected into `payment`, and the service graph showed
`checkout -> payment` and `frontend -> checkout` both 100 percent failing,
with error spans at payment 90, checkout 90, frontend 91. The service that
alerts is not the service that failed, which is what the dependency graph
exists to resolve.

## Defects found by running the stack

1. **Compose concatenates port lists, it does not replace them.** Declaring
   a loopback binding for Prometheus next to the demo's own produced two
   bindings on 9090, which would have failed at `up`. Fixed with `!override`,
   and a test now asserts every published port in the overlay is bound to
   127.0.0.1.
2. **The collector was ignoring Firebreak's configuration.** The extras file
   path comes from `OTEL_COLLECTOR_CONFIG_EXTRAS`, which still pointed at the
   empty vendored file, so the `service_graph` connector was configured and
   never loaded. The Makefile now sets it. Confirmed by the collector logging
   `Started servicegraphconnector` with component id `service_graph`.
3. **Images were not pinned.** The demo sets `DEMO_VERSION=latest`, so the
   code would have been pinned and the containers would not. Two recordings
   weeks apart would not have been comparable. `DEMO_VERSION` is now the
   submodule tag.
4. **Fault injection was editing the submodule.** This is the one that
   matters most. flagd-ui writes flag changes into the directory it serves,
   and the demo bind mounts `src/flagd` into both flagd and flagd-ui, so the
   first live injection left `vendor/` dirty with `paymentFailure` at 100
   percent. The claim that nothing under `vendor/` is edited was true of the
   code and false of the running system. Both mounts now point at
   `ops/generated/flagd`, rendered from the vendored file.
5. **Two timing assumptions were wrong.** Writing a flag and reading the
   configuration back only proves the file changed: flagd kept serving the
   old variant for 0.77 seconds afterwards. A recorder that started its clock
   on the write would label an onset before the fault existed. Separately,
   asking Locust for 20 users and reading the state back returned 5, because
   Locust ramps at `spawn_rate`. Both now wait for convergence and the flag
   path returns how long it took.

Also corrected: `docs/target-system.md` claimed this tag had no fraud
detection service. It has one, in `compose.full.yaml`, along with Kafka and
accounting. Leaving that file out is not a smaller working stack, because
the observability profile's collector scrapes Kafka either way and logged a
failure every 10 seconds.

Two more found after the stack was running:

6. **CI was not checking out the submodule.** The first Phase 1 CI run failed
   at the test step. The overlay drift tests and the flag inventory read the
   pinned demo's files on purpose, so `actions/checkout` now takes
   `submodules: true`. Those tests exist to fail when the pin moves and
   something upstream changed underneath us, which only works if the pinned
   files are there.
7. **A failing verification run overwrote a passing one.** The verification
   report was a single file, so running `lab verify` against a stopped stack
   destroyed the evidence from the run that passed. Reports are now written
   per run under a directory, named for the moment they ran.

## Known issues

**The smoke run across all flags has not happened.** It is the one
outstanding acceptance criterion. `firebreak lab smoke` exists, is covered by
tests, and turns each flag on in turn, holds it, samples Prometheus, and
turns it off. It was not run because at a 120 second hold across 15 flags it
takes about 40 minutes of a stack that this machine can only just hold, and
because two of the variants it would select are deliberately extreme
(`emailMemoryLeak` at `10000x`, `adHighCpu`) on a host with 7.8 GB allocated
to Docker. Running it is the first task of Phase 2, on the machine that
records the library.

**This machine is at the edge of what the stack needs.** Declared memory
limits total 7.9 GB against 7.8 GB allocated to Docker. Symptoms observed:
Prometheus ingestion stalled for 47 minutes during image pulls, three
collector export batches were dropped in a 15 minute window, and shell
commands repeatedly took longer than two minutes. Nothing was corrupted, and
`lab verify` reports the stack healthy now, but SPEC.md Section 23 already
prescribes the answer: record the library on a larger machine.

**Metric density was the difference between an alert firing and not.** At
the SDK default of a 60 second export interval, one series produced 5 samples
in 15 minutes and `rate(...[5m])` returned no services at all, so the two
error rate rules could never fire while the dependency edge rules, flushed
every 15 seconds by the connector, fired normally. Setting
`OTEL_METRIC_EXPORT_INTERVAL=15000` took that from 0 services with a
computable rate to 19. SPEC.md Section 6.2 wants a 15 second step for bundles
anyway, so this is the interval the library should be recorded at.

**The OpenSearch exporter is failing.** The collector logs a permanent 400
from OpenSearch on the logs pipeline, dropping log records. Metrics and
traces are unaffected. Logs are a Phase 3 signal, so this is recorded here
and fixed at the start of Phase 3 rather than now.

**Alert label leakage is a judgement call to confirm.**
`dependency_edge_failing` carries `client` and `server` labels, so the alert
that fires names the edge `checkout -> payment`. That is derived from
telemetry rather than from the fault configuration, so it is legitimate
evidence rather than ground truth, and it fires on several edges at once.
Even so, scenarios should name `checkout_error_rate_high`, the customer
facing symptom, as the triggering alert, and let the edge alerts be evidence
the agent can query.

## Open questions for the owner

1. **Where does the library get recorded?** This machine runs the stack but
   has no headroom, and a 120 scenario library at roughly 18 minutes each is
   over 30 hours of wall clock time. A cloud VM with 16 GB for Docker would
   remove the stalls and let recordings run unattended.
2. **Confirm the triggering alert for scenarios.** Recommend
   `checkout_error_rate_high` as the trigger, with the dependency edge alerts
   available as evidence. This decides what the entry gate sees first.
3. `gh` is installed but not authenticated, so phases are still merged to
   `main` with a merge commit rather than through pull requests. Run
   `gh auth login` when convenient and Phase 2 onward can use PRs.
