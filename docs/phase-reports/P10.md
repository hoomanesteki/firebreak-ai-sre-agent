# Phase 10: Feedback, memory, optimization

## Summary

Everything in this phase is a way for the system to feed its own output back into its own
input, which is the same hazard twice: a measurement that stops measuring what it claims.
Phase 10's reviewer focus states it in one line, "no validation or test data in
optimization or memory", and that line shaped most of the work.

Incident memory holds the train split only, enforced at three layers, because this is the
one leakage control in the project that guards against the system rather than against a
person. The optimizer reads train and refuses the whole task set on one violation. Prompts
became versioned files with hashes, so a report can say which prompts produced its
numbers.

**Both ablations this phase adds are currently unmeasurable, for different reasons, and
neither reason is "it did not help".** A5 scores identically to FB because memory is empty:
there are no recorded train incidents to confirm, so memory adds nothing in either
configuration. A6 refuses to run because no prompt carries an optimized lineage, since GEPA
needs a model. Reporting either as "no effect" would be a claim about memory or about GEPA;
the truth is a claim about this repository's data and credentials.

**Two things were caught by guards rather than by review, which is the point of having
them.** The leakage scanner found that the optimizer had imported the module holding
`target_service` just to read an enum value. And `COMMANDER_TOOLS` turned out to have been
declared in Phase 3 and never consumed, so `similar_incidents` was registered and
unreachable, and A5 would have been a switch that changed nothing.

## What was built

**Incident memory** (`memory/store.py`). Train-only at three layers: the model validator,
the store's `admit` raising its own `LeakageError`, and a test reading the file without
validating it. Retrieval is rarity-weighted lexical overlap plus graph overlap, ordered
deterministically.

**`similar_incidents`** (`tools/memory.py`). Returns entries phrased as leads to test, and
records the retrieval as evidence so a prior can be traced. This completes the fourteen
tools SPEC.md Section 6.3 names.

**Memory in the graph** (`consult_memory`). Adds at most two hypotheses, capped below the
three from triage, each with no supporting evidence so the exit gate's support count keeps
them advisory in practice and not only in wording.

**Feedback and promotion** (`memory/feedback.py`). Three verdicts, a required correction
when the verdict is not `correct`, per-claim indices, and a promotion that returns what it
could not do rather than logging it.

**Versioned prompts** (`prompts/`, `src/firebreak/prompts.py`). Four hand written prompts
with ids and body hashes, plus the rule that a new version is a new file.

**The GEPA runner** (`optimize/gepa.py`, `scripts/optimize_prompt.py`, `make optimize`).
DSPy 3.4.0's API confirmed against the installed package. Train-only, with a metric
combining correctness, evidence validity and calibration at stated weights.

**Ablations A5 and A6.** A5 is a switch on the run. A6 is registered and refuses.

### Two failures worth recording

**The leakage scanner refused a route I had added casually.** `optimize/gepa.py` imported
`firebreak.lab.scenario` to read `Split.TRAIN`, and that module holds `target_service` and
`fault_class`. The scanner called it a blocker, correctly: an import path to ground truth is
an import path whatever the intent. It now spells the split as a string with a test
asserting it equals `Split.TRAIN.value`, which is exactly what `memory/store.py` already
did for the same reason.

**The dependency audit failed for a real reason.** Adding DSPy pulled `diskcache 5.6.3`,
which carries `PYSEC-2026-2447` with no fix: 5.6.3 is the newest release diskcache has and
DSPy requires `diskcache>=5.6.0`, so no version satisfies both. CI now audits in two
passes, one covering what ships and what CI installs with no exceptions, and one covering
the optional developer groups with that advisory ignored by id and the reasoning written
down. The advisory has not been assessed; what bounds the exposure is that `optimize` is
never in the wheel, never installed by CI, and reached only when a developer syncs it.
`docs/threat-model.md` records it as an accepted risk the owner may reverse.

Resolving the DSPy conflict also required moving `drain3` out of the dev group, since it
pins `cachetools==4.2.1`. It is read by one script, the one that decided ADR-0006, so it
became its own group with uv told the two conflict. The test covering that script now skips
with a reason rather than being deleted.

## Deviations from the spec (with ADR links)

**Lexical retrieval rather than embeddings** (ADR-0013). An embedding model is a download,
a dependency and a source of nondeterminism in a harness whose measurements assume
reproducibility. The conditions that would reverse this are stated in the ADR: summaries
long enough that paraphrase matters, or a library large enough that lexical overlap misses
related incidents.

**Promotion does not snapshot a bundle** (ADR-0013). Recording is an eighteen minute
live-stack operation, and a function that silently did nothing without the stack would be
worse than one returning the missing step.

**No feedback HTTP endpoint.** SPEC.md Section 10.1 describes the Console asking the
questions, and the Console is Phase 11. The store and the model exist so that endpoint is
a view over them rather than a second definition of feedback.

**DSPy is an optional group with a declared conflict, and one advisory is accepted by
id.** Both described above.

## Known issues

**The whole phase is unmeasurable until the library is recorded.** Memory has no entries,
optimization has no train recordings worth the name beyond fixtures, and ID and OOD effects
have no data at all. Every mechanism is built and tested; none has produced a number worth
quoting.

**Prompt bodies are not threaded into the model calls.** They are versioned, hashed and
recorded, and `LlmClient` serves stub and replay and raises for api, so a candidate body has
nowhere to land. Wiring them in is the same work as implementing api mode and needs a model
to be worth doing. The optimization report says this in its own notes rather than leaving a
reader to infer it.

**`PYSEC-2026-2447` is accepted, unassessed.** Recorded in the threat model. Reversing the
ignore fails the build until diskcache ships a fix; removing the `optimize` group removes
prompt optimization.

**One test now skips by default.** `tests/unit/test_measurement_scripts.py` needs
`uv sync --group logcompare` for its drain3 half. Skipping is visible in the pytest output,
which is better than the alternative of deleting a test because its dependency moved.

## Open questions for the owner

1. **Model credentials.** Now blocking six things: the cost table, the cascade comparison,
   the judge's calibration, the model half of the CI gate, GEPA, and A6.
2. **AC power and the live stack.** The library is eight of one hundred and fourteen
   bundles, and every unmeasurable result in this report traces back to that.
3. **`PYSEC-2026-2447`.** Accept, or drop prompt optimization until diskcache ships a fix.
   The reasoning is in `docs/threat-model.md`; the decision is yours.
4. **Whether embedding retrieval is wanted despite the determinism cost.** The ADR argues
   not yet and states what would change it.
